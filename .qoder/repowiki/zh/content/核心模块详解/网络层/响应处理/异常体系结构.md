## ApiException类设计原理

`ApiException`类是项目中用于表示API请求异常的核心异常类，它实现了Dart的`Exception`接口。该类的设计遵循了领域驱动设计原则，通过封装HTTP请求中的业务错误码和错误消息，为上层应用提供了统一的异常处理接口。

类中定义了两个关键字段：`code`字段用于存储服务器返回的业务错误码，`message`字段用于存储用户可读的错误描述信息。构造函数提供了默认值（code为-200，message为空字符串），确保即使在异常信息不完整的情况下也能创建有效的异常实例。

通过实现`Exception`接口，`ApiException`能够被Dart的异常处理机制识别和处理，同时保持了与Dart标准异常体系的兼容性。这种设计使得开发者可以在catch块中统一处理所有API相关的异常，而不需要关心底层网络库的具体实现细节。

## 拦截器链中的异常捕获机制

在项目的网络请求处理流程中，`HttpRespInterceptor`类作为响应拦截器在拦截器链中扮演着关键角色。当API请求返回非成功状态码时（如401、403等），该拦截器会捕获这些错误并进行统一处理。

拦截器首先检查响应状态码，对于401或403等认证相关错误，会尝试自动刷新token。在刷新token的过程中，拦截器使用静态Completer来控制并发刷新，确保同一时间只有一个刷新请求在执行。如果token刷新成功，则重新发送原始请求；如果刷新失败，则拒绝请求并触发登出流程。

对于其他类型的错误，拦截器会记录错误日志，并通过`SportsToast`组件向用户显示友好的错误提示。整个过程通过`handler.reject()`方法将异常向上抛出，确保错误能够被上层的BLoC状态管理器捕获和处理。

这种拦截器链的设计实现了网络错误处理的集中化和自动化，减少了重复代码，提高了系统的健壮性和用户体验。

## BLoC状态管理中的错误状态传递

在BLoC（Business Logic Component）架构中，`ApiException`异常最终会成为状态管理中错误状态的来源。当网络请求抛出`ApiException`时，这一异常会被Controller层的try-catch块捕获，并转换为BLoC状态中的错误信息。

以登录功能为例，在`LoginCtrl`类中，submit方法通过try-catch捕获所有异常，然后调用`_getErrorMessage`方法将异常转换为用户可读的提示消息。最后通过`emit(state.copyWith(errorMessage: errorMessage))`更新BLoC状态，触发UI层的错误显示。

UI层通过`BlocBuilder`监听状态变化，当检测到`errorMessage`不为空时，会自动显示相应的错误提示。这种机制实现了错误信息从网络层到UI层的无缝传递，同时保持了各层之间的解耦。

这种设计模式确保了错误处理的统一性和可预测性，任何API请求失败都会经过相同的处理流程，最终以一致的方式呈现给用户。

## Controller/Service层的异常处理示例

在Controller或Service层捕获`ApiException`并转换为用户可读提示的典型代码模式如下：首先在业务方法中使用try-catch语句捕获异常，然后根据异常类型提取或生成合适的错误消息，最后更新状态或返回处理结果。

例如在登录Controller中，`_getErrorMessage`方法会检查异常是否为`DioException`类型，如果是则从响应数据中提取`message`字段作为错误提示。对于网络超时、连接失败等特定错误类型，会返回预定义的友好提示文本。

```dart
try {
  final response = await authService.login(request);
  // 处理成功响应
} on DioException catch (e) {
  final errorMessage = _getErrorMessage(e);
  emit(state.copyWith(loading: false, errorMessage: errorMessage));
} catch (e) {
  emit(state.copyWith(loading: false, errorMessage: '登录失败，请重试'));
}
```

这种模式确保了即使底层网络库抛出复杂的异常对象，最终呈现给用户的也是简洁明了的错误信息，提升了应用的用户体验。

## toString方法重写目的

`ApiException`类重写了`toString`方法，其主要目的是为了便于日志记录和调试。默认的异常字符串表示可能不够详细或格式不统一，通过自定义`toString`方法可以确保所有`ApiException`实例都有统一且信息丰富的字符串表示。

重写的`toString`方法返回包含错误码和错误消息的格式化字符串，如"ApiException:code:401 message:登录已过期"。这种格式化的输出在日志文件中易于识别和搜索，可以帮助开发人员快速定位问题。

在调试过程中，当异常被捕获或记录时，可以直接打印异常对象，而不需要手动拼接各个属性。这不仅简化了代码，还减少了因属性遗漏导致的调试困难。同时，统一的格式也有助于自动化日志分析工具的解析和处理。

## ApiException与DioError的区别

`ApiException`与`DioError`是两种不同层次的异常类型，它们在异常处理体系中扮演着不同的角色。`DioError`是Dio网络库抛出的底层网络异常，包含了网络连接、超时、证书验证等技术层面的错误信息。

而`ApiException`是项目定义的领域特定异常，关注的是业务层面的错误，如认证失败、权限不足、业务规则违反等。`ApiException`通常是在处理`DioError`或API响应后创建的，它将底层的技术错误转换为上层业务逻辑能够理解和处理的形式。

两者的主要区别在于抽象层次：`DioError`属于基础设施层，与具体的网络库实现耦合；`ApiException`属于应用层，与业务领域紧密相关。通过这种分层设计，应用可以独立于具体的网络库实现，便于未来的替换或升级。

## 领域特定异常封装的意义

封装`ApiException`作为领域特定异常的主要意义在于实现关注点分离和系统解耦。通过创建自定义异常类型，将网络通信的细节与业务逻辑分离开来，使得业务代码不需要了解底层网络库的具体实现。

这种封装提供了几个关键优势：首先，它创建了一个稳定的API契约，即使更换网络库实现，业务层的异常处理代码也不需要修改；其次，它允许在异常中包含领域特定的信息，如业务错误码、建议操作等；最后，它支持统一的错误处理策略，可以在一个集中的位置处理所有API相关的异常。

此外，领域特定异常还便于测试，因为可以轻松地模拟各种业务场景下的异常情况，而不需要实际发起网络请求。这种设计模式符合Clean Architecture原则，有助于构建可维护、可扩展的应用程序。
