## 命名规范
项目严格遵循Dart/Flutter社区的最佳实践和`openspec/project.md`中定义的命名约定，以确保代码的清晰性和一致性。

### 类名 (PascalCase)
所有类、枚举和mixin的名称必须使用PascalCase（大驼峰式）命名法，即每个单词的首字母大写，且不使用下划线分隔。
```dart
class LoginState { ... }
enum LoginTabType { password, verification }
class AppController extends HydratedCubit<AppState> { ... }
```
此规范在`openspec/project.md`的"命名约定"部分和`analysis_options.yaml`的`camel_case_types`规则中均有明确规定。

### 变量与方法 (camelCase)
所有变量、方法、函数和参数的名称必须使用camelCase（小驼峰式）命名法，即第一个单词的首字母小写，后续每个单词的首字母大写。
```dart
bool loginLoading;
String? errorMessage;
void submit() async { ... }
Future<void> sendVerificationCode(String phone) async { ... }
```
此规范在`openspec/project.md`的"命名约定"部分和`analysis_options.yaml`的`non_constant_identifier_names`规则中均有明确规定。

### 常量 (UPPER_SNAKE_CASE)
所有常量（使用`const`或`final`声明的顶级变量或静态字段）必须使用UPPER_SNAKE_CASE（全大写下划线）命名法，即所有字母大写，单词间用下划线分隔。
```dart
static const String appVersion = '1.0.0';
static const fontFamilyUrbanist = "Urbanist";
static const _lastLoginPhoneKey = 'last_login_phone';
```
此规范在`openspec/project.md`的"命名约定"部分有明确规定。

### 文件名 (lowercase_with_underscores)
所有Dart源文件的名称必须使用小写字母和下划线分隔符（lowercase_with_underscores）的命名方式。
```bash
# 正确的文件名
lib/pages/login/controller.dart
lib/pages/login/state.dart
lib/global/app_controller.dart

# 错误的文件名
lib/pages/login/LoginController.dart
lib/pages/login/LoginState.dart
```
此规范在`openspec/project.md`的"命名约定"部分和`analysis_options.yaml`的`file_names`规则中均有明确规定。

## 代码风格要求
项目通过`analysis_options.yaml`和团队约定，强制执行一致的代码格式，以提升代码的可读性。

### 字符串引号
项目规定优先使用单引号 `'` 来定义字符串字面量。这有助于在需要包含双引号的HTML或JSON字符串时，避免转义字符，使代码更简洁。
```dart
// 推荐
final message = '登录成功';
final html = '<div class="container">内容</div>';

// 不推荐
final message = "登录成功";
final html = "<div class=\"container\">内容</div>";
```
此约定在`openspec/project.md`的"代码风格"部分有明确规定。

### 缩进
项目使用2个空格进行代码缩进，而不是制表符（Tab）。这确保了在不同编辑器和IDE中代码的显示一致性。
```dart
void example() {
  if (condition) {
    doSomething(); // 2个空格缩进
  }
}
```
此约定在`openspec/project.md`的"代码风格"部分有明确规定。

### 行宽限制
项目设置的最大行宽为120个字符。当一行代码超过此限制时，应将其拆分为多行，以提高可读性。
```dart
// 当参数过多时，每个参数独占一行
final response = await authService.login(
  LoginRequest(
    phone: phone,
    code: code,
  ),
);
```
此约定在`openspec/project.md`的"代码风格"部分有明确规定。

## 不可变性与常量使用
项目强调使用`final`和`const`关键字来创建不可变对象，这有助于减少bug、提高性能并使代码意图更清晰。

### 使用final
尽可能将变量声明为`final`，表明其值在初始化后不可更改。这适用于所有不会被重新赋值的变量。
```dart
final formKey = GlobalKey<FormBuilderState>();
final phoneController = TextEditingController();
```
`analysis_options.yaml`中的`prefer_final_fields`和`prefer_final_locals`规则鼓励这种做法。

### 使用const
在可能的情况下，使用`const`构造函数创建编译时常量。这允许Dart编译器在编译时创建对象，从而避免在运行时重复创建，提高性能。
```dart
// 推荐：使用 const
const Text('Hello')
const SizedBox(height: 10)
const Color(0xFF7165E3)

// 不推荐：缺少 const
Text('Hello')
SizedBox(height: 10)
Color(0xFF7165E3)
```
`analysis_options.yaml`中的`prefer_const_constructors`和`prefer_const_literals_to_create_immutables`规则强制执行此最佳实践。

## 文档注释规范
项目要求使用Dart的文档注释语法来为公共API提供清晰的说明。

### 使用///文档注释
所有公共类、方法、函数和变量都应使用`///`进行文档注释。这些注释可以被`dart doc`工具解析，生成项目API文档。
```dart
/// 登录状态类，包含登录过程中的所有状态信息。
class LoginState {
  /// 是否正在登录中。
  bool loginLoading;

  /// 发送验证码。
  ///
  /// [phone] 参数为要发送验证码的手机号码。
  Future<void> sendVerificationCode(String phone) async { ... }
}
```
`analysis_options.yaml`中的`slash_for_doc_comments`规则要求使用`///`而不是`//`进行文档注释。

## 静态分析与Lint规则
项目通过`analysis_options.yaml`文件配置了全面的静态分析规则，以在编码阶段捕获潜在错误和不一致的代码风格。

### Lint规则配置
`analysis_options.yaml`文件定义了超过100条lint规则，涵盖了命名、格式、性能和最佳实践等多个方面。这些规则的严重性级别被设置为`info`，意味着它们会作为警告或提示出现在IDE中，但不会阻止代码编译。
```yaml
linter:
  rules:
    - camel_case_types
    - non_constant_identifier_names
    - file_names
    - prefer_const_constructors
    - prefer_final_fields
    - avoid_print
    - prefer_is_empty
    # ... 更多规则
```
这些规则确保了代码库的一致性，并帮助开发者遵循最佳实践。

### 关键Lint规则
- **`avoid_print`**: 禁止在生产代码中使用`print()`语句，鼓励使用项目定义的日志工具`l.d()`、`l.i()`等。
- **`prefer_is_empty`**: 建议使用`isEmpty`或`isNotEmpty`来检查集合是否为空，而不是`length == 0`，因为前者性能更好且更清晰。
- **`prefer_const_constructors`**: 鼓励在可能的情况下使用`const`构造函数，以提高性能。
- **`prefer_final_fields`**: 建议将类字段声明为`final`，除非需要在构造函数之外修改它们。

## 预提交钩子
项目配置了Git预提交钩子（pre-commit hook），在代码提交到版本控制系统之前自动执行一系列质量检查，确保只有符合规范的代码才能被提交。

### 钩子执行流程
`scripts/pre-commit.sh`脚本定义了预提交钩子的执行流程：
1.  **暂存未暂存的更改**：首先，脚本会将工作区中未暂存的更改临时存储起来，以确保格式化操作只影响已暂存的文件。
2.  **运行Dart格式化工具**：执行`dart format .`命令，根据Dart官方格式化指南自动格式化所有Dart文件。
3.  **运行Flutter分析器**：执行`flutter analyze`命令，运行`analysis_options.yaml`中定义的所有静态分析规则。如果发现任何错误，提交将被中止。
4.  **恢复暂存的更改**：最后，脚本会将之前暂存的更改恢复到工作区。

### 自动化质量保证
此预提交钩子是项目质量保证流程的关键部分。它强制执行代码风格和静态分析规则，确保了代码库的整洁和一致性，减少了代码审查中关于格式问题的讨论，让团队可以更专注于业务逻辑和架构设计。
