## 简介
本项目通过 `HttpRespInterceptor` 实现了统一的HTTP响应处理机制，确保前后端交互的数据格式标准化。该机制基于 `BaseResponse` 统一响应结构，对服务器返回的数据进行标准化处理，根据业务状态码判断请求成功与否，并将实际数据体传递给后续处理链。当请求失败时，系统会统一进行错误处理，包括Token自动刷新、错误提示等。

## 核心处理流程

`HttpRespInterceptor` 的 `onResponse` 方法是整个响应处理的核心，其主要职责是将原始响应数据转换为 `BaseResponse` 对象，并根据业务状态码决定后续处理流程。

处理流程如下：
1. 将原始响应数据解析为 `BaseResponse` 对象
2. 判断业务状态码是否为成功（code=1）
3. 若成功，提取data字段作为实际数据体并传递给后续处理链
4. 若失败，调用 `handleResponseError` 进行错误处理

```mermaid

Start([开始处理响应]) --> ParseResponse["解析为BaseResponse对象"]
ParseResponse --> CheckCode{"业务码是否为1?"}
CheckCode --> |是| ExtractData["提取data字段"]
ExtractData --> PassData["传递给后续处理链"]
CheckCode --> |否| LogError["记录错误日志"]
LogError --> HandleError["调用handleResponseError"]
HandleError --> End([结束])
```

## BaseResponse 统一响应结构

`BaseResponse` 类定义了统一的响应数据结构，确保所有API接口返回的数据格式一致，便于前端统一处理。

```dart
class BaseResponse {
  dynamic data;
  int code;
  String? message;
  String? requestId;
  
  BaseResponse(this.data, this.code, this.message, this.requestId);
  
  factory BaseResponse.fromJson(Map<String, dynamic> json) {
    return BaseResponse(
      json['data'],
      json['code'] as int,
      json['message'] as String?,
      json['requestId'] as String?,
    );
  }
}
```

### 设计目的
- **标准化**: 统一所有接口的响应格式，降低前端处理复杂度
- **可维护性**: 集中处理响应逻辑，便于后续修改和扩展
- **错误处理**: 包含完整的错误信息（code、message、requestId），便于问题定位
- **扩展性**: 支持任意类型的数据体（dynamic data），适应不同业务场景

### 前后端交互作用
- **前端**: 无需关心具体接口的返回格式，统一通过 `BaseResponse` 处理
- **后端**: 只需遵循统一的响应结构，无需为每个接口单独定义格式
- **调试**: 通过 `requestId` 可以快速定位问题请求，提高排查效率

## 正常响应处理时序

当服务器返回成功响应时，`HttpRespInterceptor` 会提取data字段并传递给后续处理链。

```mermaid
sequenceDiagram
participant Client as "客户端"
participant Interceptor as "HttpRespInterceptor"
participant Handler as "处理链"
Client->>Interceptor : 返回响应数据
Interceptor->>Interceptor : BaseResponse.fromJson(response.data)
Interceptor->>Interceptor : 检查res.code == HttpCode.success
Interceptor->>Handler : handler.next(Response(data : response.data['data']))
Handler->>Client : 处理实际数据体
```

### 实际请求响应示例
```json
{
  "code": 1,
  "message": "操作成功",
  "requestId": "req-123456789",
  "data": {
    "userId": 123,
    "userName": "张三",
    "email": "zhangsan@example.com"
  }
}
```

在上述示例中：
- `code=1` 表示业务成功
- `message` 提供人类可读的成功信息
- `requestId` 用于追踪请求
- `data` 包含实际的用户信息数据体

## 错误响应处理流程

当业务状态码不等于1时，系统会将控制权交给 `handleResponseError` 方法进行错误处理。

### 错误处理机制
1. 记录详细的错误日志，包含路径、状态码、消息和请求ID
2. 根据错误类型进行差异化处理
3. 特殊处理401/403错误（Token过期）
4. 显示友好的错误提示

```mermaid
flowchart TD
Start([开始错误处理]) --> CheckStatus{"状态码401/403?"}
CheckStatus --> |是| CheckRefreshPath{"路径为/auth/refresh-token?"}
CheckRefreshPath --> |是| Logout["登出用户"]
CheckRefreshPath --> |否| CheckRefreshing{"正在刷新Token?"}
CheckRefreshing --> |是| WaitRefresh["等待刷新完成"]
CheckRefreshing --> |否| StartRefresh["开始刷新Token"]
StartRefresh --> CallRefreshAPI["调用刷新Token接口"]
CallRefreshAPI --> UpdateToken["更新AppController中的Token"]
UpdateToken --> RetryRequest["重新发送原始请求"]
WaitRefresh --> CheckResult{"刷新成功?"}
CheckResult --> |是| RetryRequest
CheckResult --> |否| Logout
Logout --> ShowToast["显示'登录已过期'提示"]
Logout --> Reject["拒绝请求"]
CheckStatus --> |否| CheckMessage{"有message字段?"}
CheckMessage --> |是| ShowMessage["显示message内容"]
CheckMessage --> |否| ShowDefault["显示'网络错误'"]
ShowToast --> Reject
ShowMessage --> Reject
ShowDefault --> Reject
Reject --> End([结束])
```

### Token自动刷新机制
系统实现了Token自动刷新机制，确保用户体验的连续性：

```mermaid
sequenceDiagram

participant AuthService as "AuthService"
participant Server as "服务器"

Interceptor->>Interceptor : 检查是否正在刷新
Interceptor->>AuthService : 调用refreshToken接口
AuthService->>Server : 发送刷新请求
Server->>AuthService : 返回新Token
AuthService->>Interceptor : 返回AuthResponse
Interceptor->>Interceptor : 更新AppController中的Token
Interceptor->>Interceptor : 重新发送原始请求
Interceptor->>Client : 返回成功响应
```

## 总结
`HttpRespInterceptor` 实现了一套完整的响应处理机制，通过 `BaseResponse` 统一响应结构，确保了前后端交互的标准化。该机制具有以下优势：

- **统一性**: 所有接口遵循相同的响应格式
- **自动化**: 自动处理Token刷新，提升用户体验
- **可维护性**: 集中处理响应逻辑，便于维护和扩展
- **可调试性**: 完整的错误信息和日志记录，便于问题排查

开发者在使用时只需关注业务数据体（data字段），无需关心底层的响应处理细节，大大提高了开发效率和代码质量。
